# CLEC native Phase 2 corrective issues

This ledger records confirmed Unit A defects found during independent review of head `f4d04a7` and tracks each verified fix.

## Unit A findings and resolutions

1. **`P2-DETERMINISM-CANONICAL-MAP`: `clec-publish` produces non-deterministic SQLite and `.zst` hashes across identical runs.**
   At `f4d04a7`, `native/src/snapshot.rs` builds `groups: HashMap<(String, SourceRole, String), Vec<usize>>` and iterates `groups.values()` when inserting rows into `source_canonical_map`. Three identical synthetic builds with multiple equivalence groups produced three distinct SQLite SHA-256 digests (`847844f4...`, `4df2948d...`, `d1715021...`, recorded in `.cache/before-repro/before_repro.json`).
   **Resolution (`6f1bab0`, verified at `83f7738`).** `native/src/domain.rs` derives `PartialOrd, Ord` on `SourceRole`, and `native/src/snapshot.rs` replaces `HashMap` with `BTreeMap` and sorts `source_canonical_map` rows by `(work_id, role, equivalence_hash, source_id)` before schema inserts. Synthetic unit tests (`publish_is_byte_deterministic_across_repeats_and_input_permutations`), `verify_phase2.py` (`deterministic_repeat_publish`), and two sequential full-corpus builds all produced byte-identical SQLite (`7e106db6b5f06287d4a8e8d1323af2c5098cc702719f8aa310aa75af8df610a0`, `1,058,476,032` B) and `.sqlite.zst` (`34a01433e41a7b71e635f4aa1ddac5f6c99a05dcce2a453ae0e9e264a7f73f66`, `327,255,080` B) outputs.

2. **`P2-CAPACITY-DELETED-ARTIFACTS`: Deleted `a409...` capacity-run artifacts leave table-content equality unproved.**
   In the prior worktree's `.cache/phase2/capacity-run/`, the built `.sqlite` and `.sqlite.zst` files for `a4091fa6...` were removed after `capture_capacity.py` ran, even though `capacity-report.json` recorded `"artifactsKept": true`. Aggregate row counts matched `5b14`, but row-level content and posting equality were not verified.
   **Resolution (`83f7738` and `.cache/phase2/` receipts).** `docs/agent-work/clec-native/phase2-report.md` records an honest correction noting that the deleted `a409...` artifacts could not prove table-content equality. A fresh full-corpus `capture_capacity.py --keep-artifacts` run retains the deterministic `7e106db6...` release, synced SQLite DB, and `/usr/bin/time -l` logs under `.cache/phase2/capacity-run/`. `evaluation/clec-v1/phase2/semantic_compare.py` proves exact SHA-256 equality between the preserved `5b14` reference DB and `7e106db6` across all `10` domain tables (`metadata`, `works`, `blobs`, `sources`, `source_canonical_map`, `source_diagnostics`, `cues`, `inventory`, `passages`, `passage_spans`) and all `37,690,846` FTS5 postings mapped by `PassageId` (`f1d51579b655c3a170e34972aba00120b81da57c0a928891875f1ecbbea09cc0`).

3. **`P2-CAPACITY-MEASUREMENT-CONTRACT`: `3.0016 GB` figure is a scoped component estimate, and `capture_capacity.py` sets only `TMPDIR`.**
   At `f4d04a7`, `capture_capacity.py` sets only `TMPDIR` (omitting `SQLITE_TMPDIR`, `TEMP`, `TMP`), walks directories for logical byte size only (omitting allocated disk blocks), and labels `sqliteBytes + 2 * postingBucketSetBytes + 65536` as a conservative worst-case storage bound without listing excluded SQLite journals, temp B-tree spills, filesystem allocation slack, and OS buffers.
   **Resolution (`83f7738`).** `evaluation/clec-v1/phase2/PROTOCOL.md` and `evaluation/clec-v1/phase2/capture_capacity.py` now set `TMPDIR`, `SQLITE_TMPDIR`, `TEMP`, and `TMP` explicitly inside the measured temp tree, report both logical bytes and allocated disk blocks (`st_blocks * 512`) as `polled_50ms_sampled_lower_bound`, extract `estimate_posting_buckets_bytes` cleanly without narration comments, and separate `scopedComponentStorageEstimate` with explicit `uncoveredOverheads`. All `14` baseline workspace hashes under `/Users/century/vibing/clec` remained unchanged before and after the run.
