## 问题与依据

`answer-protocol-investigation-20261111.md` 记录五次真实失败：完整 JSON 的 gap 多带 evidenceIds，被 `domain/answer.ts` 的精确字段校验拒绝。两次最新复现还在 gap 中陈述来源内容的缺失情况。已有提示虽列出三种结构，仍未稳定使模型遵守。当前失败是产品验收失败，不能改写为正常缺证回答。

## 实施边界

1. `qa/resources.ts`：明确 gap 只能有 kind、text，禁止 evidenceIds；answer/context 承载有证据的事实，gap 只表述尚不能回答的用户问题。没有未答部分时不必生成 gap，禁止为未被问及的工具、步骤等附加问题制造缺口。增加一个短的 context+gap 合法示例，示例 handle 须标明占位符、不可直接引用。不能用提示鼓励把无法支持的负面事实机械搬进 context。
2. `domain/answer.ts`：继续纯结构校验和严格拒绝。加入有限的内部拒绝原因，至少区分无效 JSON、结构/额外字段、gap 额外字段、文本界限、未知证据、引用结构以及缺少 answer/gap。用一个局部类型化错误承载原因即可，不建立通用验证框架。不得自动删字段、修复 JSON、重试模型或扩大预算。
3. `qa/pi.ts` 与 `diagnostics/*`：将该内部原因映射为固定白名单字段；磁盘序列化也必须验证白名单。保留公开错误与无最终结果的原子失败行为。不得记录模型文本、字段原值、动态键名、证据 ID、异常堆栈或内容摘要。保持现有日志大小、轮转、丢弃与不抛异常约束。
4. `qa/budget.ts`：对照锁定 Pi 类型和实际 transcript 的 sections/preamble/toolsAdded 结构修正组件计量。总准入仍以完整 context 的 UTF-8 JSON 字节加原有输出保留量计算，4 次调用及累计限额不变。组件数并非网络请求字节数，不要求其求和等于总值；缺少结构时应保守报告，不伪造已观察的组件。
5. 不修改会话 schema、证据授权、检索、QMD 补丁、依赖或 API 返回契约。若实际类型使以上局部边界无法自然实现，先交回主审说明，不扩大重构。
